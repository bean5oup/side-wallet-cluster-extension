## 현재 확정 작업 방식 — BigQuery API/CLI

사용자가 BigQuery를 기존 API/CLI 방식으로 사용하는 것을 확정했다. 이 절이 현재 작업 순서와 공급원 선택의 기준이다. 아래 과거 단계의 수치와 handoff는 당시 관측 기록으로 유지한다.

| 구간 | 담당 |
|---|---|
| Fomo 계정·순위·BUY/SELL/THESIS 시점 | 기존 Fomo REST collector 및 checkpoint |
| 과거 전송·token-account owner 활동·연관 지갑 후보·토큰별 event window | BigQuery SQL을 인증된 `bq` CLI/API로 조회 |
| 중요한 거래의 성공·swap·quote·fee와 누락 보완 | RPC/Etherscan 원문 |
| 크로스체인 deposit/order/destination 대응 | 기존 local Bridge API + 직접 RPC 근거 |
| 원본·정규화·타임라인·inventory/PnL 입력 저장과 재계산 | SQLite/Python |

Query project는 `exchange-labs`로 명시한다. Ethereum은 `US`, 현재 Solana dataset은 `us-central1`로 조회한 뒤 로컬에서 합친다. MCP는 필수 수집 경로로 두지 않으며 Dune은 현재 수집에서 제외한다. 신규 API 키를 코드나 문서에 넣지 않는다.

### 결과 회수·저장 기준

- SQL 원문/hash/version, project/dataset/location, wallet/token parameter, UTC 조회 구간, job ID, capture time과 raw result page를 보존한다.
- Dry-run 추정량, 실제 processed/billed bytes, cache 여부, totalRows/fetchedRows와 pagination 상태를 기록한다. CLI의 기본 출력 행 수나 LIMIT를 전체 history로 취급하지 않는다.
- 모든 page를 회수하고 반환 전체 행 수를 확인해야 result retrieval을 complete로 기록한다. History coverage는 indexed block 범위·known transaction 대조·provider gaps로 별도 기록한다.
- EVM uint256과 token amount는 정확한 문자열/정수로 유지한다. Transfer와 swap, Fomo BUY와 THESIS 및 on-chain 시간은 별도 field다. 같은 추출을 재적재해도 원본과 normalized 행을 중복하지 않는다.
- 결과를 SQLite에 보존해 파싱·timeline·원가 계산을 반복할 때 cloud history를 다시 스캔하지 않는다.

### Dune SQL/API — 과거 검토 기록, 현재 제외

- 2026-10-06 공식 Dune 데이터 카탈로그에서 Solana DEX 테이블 `dex_solana.trades`를 확인했다. `trader_id`, `tx_id`, `block_time`, token mint 및 수량 필드가 있어 지갑별 swap history를 SQL로 조회할 수 있다. 한 트랜잭션에 여러 trade row가 있을 수 있고, 이 테이블은 DEX trade 데이터이므로 전체 transaction/transfer 기록과 같지 않다. ## 3. Current research model and boundaries

- Raw provider responses, trader/snapshot/event/on-chain rows와 파생 research rows를 SQLite에 보존한다. 이벤트 및 signature key로 중복 매칭을 막는다. CSV는 DB에서 재생성하는 export다.
- 현재 수집 역할은 `Fomo REST → SQLite`, `BigQuery API/CLI → raw result pages + job provenance → SQLite`, `RPC/Etherscan → 중요한 거래 검증·누락 보완`, `Bridge API → source/order/destination 대조`다. SQLite가 연구 기준 저장소이며 CSV는 선택적 export다. BigQuery 수집기는 상단의 다음 구현 순서에 따라 추가한다.
- Fomo BUY, SELL, THESIS/CALL, on-chain BUY/SELL 시점은 별도 UTC timestamp로 유지한다. 단순 transfer를 swap으로 취급하지 않는다.
- 사용자 승인에 따라 1차 조사 범위를 최신 30d leaderboard Top 10 파일럿으로 확장했다. 주소 inventory는 `data/research/top10_wallet_inventory.csv`, 검증된 event match 표는 `data/research/top10_event_trade_matches.csv`에 로컬로 생성했다. 두 파일은 `.gitignore` 대상이다.
- Top 10의 Solana/EVM 주소는 후보에서 시작한다. 현재 Solana rank 1·5·9·10과 Ethereum rank 8·9가 두 개의 독립 event/signature match로 verified이고, rank 3 및 rank 8 Solana는 ambiguous다. 다른 EVM chain의 주소 resolution은 미확인이다. QuickNode에서 rank 1·5·9의 60일 경계까지 29,600 full transaction rows(148 pages)를 가져왔고, rank 10의 3,782개 전체 반환 기록도 보존했다. `build-timeline` 결과 SQLite에는 33,382 wallet/signature actions, 51,885 token deltas, 27 Trader × Token rows가 있다. ## 4. Risks and unknowns

- API 공급자의 보관 기간, Fomo history completeness, Fomo timestamp 의미, 장기 REST gap의 완전 복구는 unknown이다.
- 83건·136건·94건·112건은 각각 별도의 과거 WebSocket 단기 수집 결과이며 gap-free history를 보장하지 않는다. REST Top 10 pull은 API가 돌려준 현재 접근 가능 구간일 뿐, 2026-10-03 이전 feed 보존 여부는 확인되지 않았다. 단일 snapshot은 과거 leaderboard 변동을 복원하지 못한다.
- Helius, QuickNode, shared public RPC가 verified 주소의 가장 오래된 서명으로 2026-08-24를 반환했다. Top 10 signature probe에서는 8/10 주소가 60일 cutoff 이전 기록을 반환했고 두 주소는 35일/42.6일 이력 끝에서 pagination이 종료됐다. 주소의 최초 관측일은 wallet keypair 생성일과 다를 수 있다.
- 거래 action 분류는 swap log + signer + opposing balance change 및 transfer log + token delta를 사용하는 휴리스틱이다. 토큰별 quote는 이 표본에서 USDC로 확인했지만, Fomo의 reported `usdValue` 의미는 온체인 지출과 일치하지 않는다. SPL/router decoder review, transfer cost basis, 사후 exit, DEX/protocol 식별, fee-payer 귀속, fee의 USD 환산, X user/post coverage 및 장기 rate/SLA 검증은 남았다.
- Indexed/curated 데이터의 행 수만으로 전체 지갑 이력의 coverage를 판단하지 않는다. 현재 BigQuery 결과는 transaction signature와 log/event index 단위 매칭, Fomo event 핵심 거래 보존, 누락·중복 및 반환 기간으로 검증한다. 과거 검토한 Dune `dex_solana.trades`도 비DEX action, 단순 transfer, 실패 transaction을 모두 대표하지 않는다.
- BigQuery block 최신성 확인은 다른 모든 테이블의 coverage를 보장하지 않는다. Solana Token Transfers의 source/destination/authority 의미와 owner history 누락, Ethereum event_index 대응은 개별 거래로 검증해야 한다. Dune의 접근·비용·보관 제한은 아래 과거 검토 기록이며 현재 수집 의존성이 아니다.

## 10. BigQuery 적용 작업과 크레딧 운영 — 2026-10-06

사용자가 약 40만원의 Google Cloud 크레딧을 보유하고 있으며 비용이 클 때만 알리도록 요청했다. 운영상 큰 비용은 우선 작업 묶음의 예상 비용 5만원 이상으로 해석한다. 이 숫자는 사용자가 지정한 한도가 아니라 현재 agent의 가정이다. 조회량은 매번 dry run과 maximumBytesBilled로 통제하고, 실제 job 처리량과 누적 연구 사용량을 기록한다. 예정 작업이 보고된 잔여 예산을 소비할 때는 알린다. 이후 사용자와 API/CLI 방식을 확정했다. 현재 작업 순서는 상단 절을 따른다. 이후 고정 30일 Ethereum ERC-20 job 1개를 실행했으며 실제 billed bytes는 35,100,033,024다. 같은 job에서 결과를 두 페이지로 받았고 parser 보완 뒤에는 저장된 페이지로만 적재해 재조회하지 않았다.

1. **검증 지갑의 historical coverage 보완:** RZD Ethereum의 고정 30일 token-transfer 이력을 기존 34개 ERC-20 log와 대조하고, Solana의 알려진 bridge 수령 7건을 owner/token-account 단위로 확인한다. 구조와 결과가 맞으면 RZD Solana owner-history 30일 추출을 한 번 수행하는 방안을 비용 범위 안에서 검토한다. 3. **Thesis token 중심의 선행·후행 거래 후보 검색:** Fomo의 실제 BUY/THESIS timestamp를 기준으로 token contract/mint와 작은 event window를 BigQuery query input으로 사용한다. 자금 관계 후보가 call 전에 같은 token을 취득하거나 이후 처분했는지 찾고 중요한 거래의 실제 swap/quote/fee는 receipt 또는 instruction으로 해석한다. Token transfer는 매수로 자동 분류하지 않으며 아직 오지 않은 event 후반 window는 incomplete로 표시한다.
4. **중복·누락 점검 및 집계:** 기존 RPC/Etherscan 결과와 chain/transaction/log-or-instruction/wallet grain을 맞춰 차이를 찾고, 최초 관측 활동·전송 합계·빈도·event-time 차이를 계산한다. Coverage gate를 통과한 결과만 normalized timeline과 inventory로 연결한다. 최초 관측이 lifetime first라는 결론을 내리지 않는다.
