## 우선순위 1 — 10명의 과거 기록에서 조사할 사건을 선정한다

**답할 질문:** 누가, 언제, 어떤 토큰을 공개하거나 실제 매수했으며 그 당시 저시총 조건을 충족했는가?

1. 각 계정의 기존 Fomo 원문, chain별 지갑 후보/검증 상태, API cursor와 이미 수집한 거래를 먼저 재사용한다.
2. REST로 60일 THESIS/CALL/BUY/SELL에서 빠진 기간과 페이지를 순차 보완한다. 동일 trade ID의 반복 알림을 여러 번의 실제 체결로 세지 않는다.
3. 정확한 chain/contract/mint, source ID, 게시 시각, 실제 거래 시각, 수집 시각을 계정×토큰 시간표로 정리한다. BUY의 실제 대외 노출 시각은 별도이며 확인하지 못하면 unknown이다.
4. 필요한 후보 거래의 성공, 최종 토큰 수령자/owner, 실제 quote 부담자와 raw 수량을 검토한다. 토큰 수령만 확인된 후보를 매수나 소유권 증명으로 승격하지 않는다.
5. 그 기준 이벤트 당시 역사적 유통 시총을 확인해 적격/상한 초과/근거 부족으로 구분한다. 현행 최대 300초 시총 표본 차이는 연구자가 둔 운영 가정이며 사용자가 정한 것은 $1M 상한이다. 표본 불확실성과 판정 불가 원인을 남긴다.

**산출물:** 10명 진행표, 계정×토큰 시간표, 확보 기간/누락 목록, 적격 사건 대기 목록. 기존 일부 온체인 60일 capture가 있어도 Fomo 기록과 지원 체인 전체의 통합 coverage가 완료된 것으로 취급하지 않는다.

**다음 단계:** 적격 사건이 나오면 1~3개를 우선순위 2에 배정한다. 10명 전원의 모든 수집 완료를 기다릴 필요는 없다. 처음에는 사건 시각·지갑·시장 자료가 검증 가능한 사례를 택해 분석 경로를 완성하고, 미확보/미지원 체인의 편향을 함께 기록한다. 결과가 의심스러운 사례만 골라 긍정 사례 수를 높이지 않는다.

## 우선순위 2 — 토큰 1~3개에서 선행 매수부터 자금 회수까지 추적한다

**답할 질문:** Fomo 공개 또는 실제 매수에 앞서 같은 토큰을 산 외부 지갑이 있으며, Fomo 지갑과 자금 관계가 있고, 이후 어떤 경로로 처분/회수했는가?

1. THESIS/CALL이 있으면 확보한 게시 시각을, BUY-only면 검증된 실제 매수 시각을 기준으로 삼는다. 공개가 더 앞서 있었다면 그 기록도 함께 비교한다. THESIS 전 매수와 확보한 최초 공개 전 매수, Fomo 매수 전 매수를 구분한다.
2. 기존 운영 가정인 전 2시간/후 1시간에서 관련 풀과 migration을 확인하고 실제 swap의 최종 매수자를 추출한다. 10/30/60초 및 5/15분 창의 시간 간격과 매수 수량을 비교한다. 이 범위는 시장의 전체 lifetime history가 아니다.
3. 근접 매수 후보를 배경 거래 빈도, 봇/MEV/라우터, 반복 체결 여부와 대조한다. 본지갑의 추가 매수와 다른 지갑의 매수를 구분한다. 동시 매수만으로 조직적 선행매수라고 판정하지 않는다.
4. 후보 지갑에 돈을 보낸 비서비스 공급자, Fomo 지갑과의 실제 송금, token 반환, quote 회수와 중간 주소를 따라간다. 공유 거래소 출금 지갑·Relay solver·aggregator 경유는 소유권 근거가 아니다.
5. 초기에는 기준 이벤트 후 24시간까지 실제 매도와 quote 수령을 확인하고, 고정 기간 안에서 관측된 후속 회수 경로가 있으면 필요한 후속 구간을 배정한다. 매도 수령 quote와 이후 전송의 연결 근거, 혼합 잔고와 이전 재고의 불확실성을 함께 기록한다.
6. Bridge는 source deposit/order/destination을 양쪽 거래로 대응시킨다. CEX는 정확한 chain/recipient와 고객 deposit 역할 근거를 각각 확인해 Fomo 지갑 및 후보와 비교한다. 라벨은 provider assertion, 실제 전송은 독립 거래 근거로 보존한다.

탐색할 구조는 `외부 후보의 취득 → 기준 이벤트 → 후보의 처분/quote 수령 → 중간 지갑/bridge → CEX 입금 후보`와 `Fomo 지갑 → 자금 공급·반환·회수 또는 같은 입금 후보`의 접점이다. 이 구조는 조사 목표이며 현재 확인된 공통 회수 구조라는 뜻은 아니다.

**산출물:** 사례별 한글 보고서, 실제 tx/시각/raw 수량을 연결한 구조도, 후보 지갑 목록, 처분/회수 경로, exact CEX endpoint 비교, coverage gap. 실제 원가·매도·quote·fee·이전 재고/이전 lot 원가가 충족되지 않으면 실현 수익은 unknown이다.

**완료 기준:** 배정된 시간/체인 범위에서 거래와 연결 근거를 검토하고 확정/후보/미관측/미확보를 구분해 제출한다. 공통 CEX가 반드시 나와야 완료되는 것은 아니다. 고객 deposit을 못 찾은 경우와 조회 자체를 못 한 경우를 분리한다.

## 우선순위 3 — 10명과 여러 토큰에서 연결의 반복성을 비교한다

**답할 질문:** 한 사례의 후보 지갑·공급자·회수 지점이 다른 토큰이나 다른 Fomo 계정에서도 반복되는가?

- 주소×계정×토큰×사건의 표로 같은 후보, 비서비스 funder, 중간 회수 주소, 정확한 고객 deposit endpoint를 교차 비교한다. 명단 밖의 공개 매수 지갑이 여러 사례에서 등장하면 같은 후보로 연결하되 독립 계정 조사는 자동 시작하지 않는다.
- 같은 지갑의 선행 취득과 공개 이후 처분이 여러 사건에서 반복되는지, 같은 Fomo 지갑으로 token/quote가 돌아오는지 확인한다.
- 같은 CEX 이름·hotwallet·solver의 중복과 실제 동일한 chain/address의 고객 입금 후보 중복을 구분한다. 동일 deposit 중복도 통제/공모/의도를 단독 확정하는 근거로 쓰지 않는다.
- 지갑 간 연결, 사건의 시간 순서, 이후 매도, 원가/수익은 각각 평가한다. 약한 추정들을 합쳐 verified ownership으로 승격하지 않는다.

**산출물:** 10명 교차 비교표, 반복 경로 구조도, 근거별 강도/한계, 추가 확인할 거래 목록. 우선순위 2의 사례가 하나 끝날 때마다 갱신할 수 있으므로 전체 조사 종료까지 기다리지 않는다.

**확장 판단:** 10명의 실제 coverage, 완료된 1~3개 사례의 방법과 누락, 요청량/비용을 검토한 뒤 다음 10명 확대를 정한다. 유의미한 연결이 없더라도 분석이 충실했다면 결과로 보존한다. 부정적 사례와 미확보 사례도 확장 판단에 포함한다.

## 데이터 수집과 Chrome 추적 — 2026-10-07 추가 지시

기존 Fomo REST·indexed API·RPC와 저장 자료를 기본 경로로 사용하고, BigQuery는 적격 토큰의 넓은 후보 검색과 특정 누락 보완에 선택적으로 사용한다. 사용자 지시에 따라 개별 지갑·CEX 연결 추적에는 **보이는 Chrome**에서 Arkham과 해당 체인의 탐색기를 연다.

| 단계 | 기본 경로 | BigQuery를 사용할 때 | Chrome에서 확인할 내용 |
|---|---|---|---|
| 1. 초기10명 기록/선별 | SQLite 재사용 → Fomo REST, indexed API/RPC, 역사적 시총 자료 | 기존 경로의 특정 과거 거래 누락을 SQL로 대조할 필요가 있을 때 | 필요한 계정/거래 페이지와 주소 후보를 보조 확인 |
| 2. 적격토큰1~3개 사례 | 기존 캡처·관련 pool 자료와 실제 swap 근거 | 아직 모르는 매수 지갑을 token/time 범위에서 검색하거나 여러 지갑·시각을 함께 비교할 때 | Arkham 상대 지갑·라벨·입출금 방향, 체인 탐색기의 실제 tx·token/native/internal 이동 |
| 3. 10명/토큰 교차 비교 | SQLite의 exact 주소·event·edge 비교 | 여러 후보의 같은 기간 기록에서 구체적인 빠진 근거가 있을 때 | 공통 회수/입금 후보의 실제 역할과 거래 재확인 |

### BigQuery 실행 선택

- Google 공식 지원표에서 Ethereum/Arbitrum 등과 community Solana 자료를 확인했다. 기존 연구는 Ethereum `goog_blockchain_ethereum_mainnet_us`와 Solana `crypto_solana_mainnet_us`를 사용했다. 체인별 실제 schema·location·최근 적재 시점·요청 기간 coverage를 다시 확인한다. BSC/Robinhood Chain 등은 기존 Nodit/RPC/탐색기 경로를 유지하고 추가 BQ dataset은 실제 검증 후 사용한다. [Google 지원표](https://docs.cloud.google.com/blockchain-analytics/docs/supported-datasets)
- 적격 사건의 정확한 chain/token/pool·시간과 필요한 열을 지정한다. 먼저 dry run으로 조회량을 추정하고 기존 기본 cap 40GiB를 적용한다. 이를 넘으면 projection·partition 조건·중복 구간 병합·indexed source를 검토한 뒤 근거와 비용을 기록해 cap/작업 범위를 결정한다. 예상 비용이 크면 실행 전에 알린다는 기존 사용자 선호를 따른다. 현재 묶음5만원 안내 기준은 연구자의 임시 운영 가정이다.
- 작은 시간 창이나 token 조건이 실제 읽는 용량을 작게 만든다고 가정하지 않는다. 파티션/클러스터 조건과 dry run을 확인한다. `LIMIT`만으로 비용을 통제하지 않으며 `maximumBytesBilled`를 명시한다. [Google 비용 통제](https://docs.cloud.google.com/bigquery/docs/best-practices-costs)
- 기존 실측은 Ethereum 한 collection `35,100,033,024` billed bytes, Solana 세 collection 합 `12,067,997,220,864` billed bytes(약10.976TiB)다. 서로 다른 query/scope의 사용량이며 새 토큰 조회의 예상치나 실제 청구 금액/잔여 크레딧을 뜻하지 않는다. 새 작업은 별도 dry run으로 정한다.
- 한 번 회수한 완전한 결과는 SQLite/raw에서 재사용한다. 쿼리·parameters·estimated/cap/actual bytes·job·페이지·source coverage를 보존한다. Transfer나 balance 변화 후보를 실제 BUY로 자동 분류하지 않는다. 같은 source의 반환 결과 회수 완료와 전체 시장 coverage는 구분한다.
- BigQuery는 과거 유통 시총이나 고객 CEX 소유권을 단독 확정하는 경로가 아니다. 시총 근거, 실제 swap/owner/quote, 거래소 라벨과 고객 deposit 역할을 각각 검토한다. 이번 방향 갱신에서 유료 query는 실행하지 않았다.

### Chrome 사용과 근거 저장

1. 본체가 Chrome의 기존 연구 탭/로그인 상태를 확인해 사용하거나 담당 주소/tx의 새 탭을 연다. 사용자가 지정한 Chrome을 추적 화면으로 사용한다. 로그인/권한 부족은 실제 상태를 확인해 gap으로 기록한다.
2. Arkham에서 counterparties·funding/outflow·거래소 라벨과 개별 tx를 확인하고 해당 체인의 탐색기로 실제 주소와 방향을 대조한다. Ethereum은 Etherscan, 다른 체인은 실제 chain과 공식 탐색기 경로를 확인한다.
3. 페이지 URL·관측 UTC·정확한 chain/address·tx/signature·라벨과 유형·관련 화면 근거·페이지/기간/접근 제한을 보존한다. 쿠키·인증 URL·무관한 사용자 화면은 저장하지 않는다.
4. 핵심 transfer·swap·Bridge 양쪽 거래는 기존 독립 RPC proof와 대조하거나 예약한 한도에서 조회한다. Arkham의 entity/AI 예측·exchange aggregate는 provider assertion이며 동일 고객/소유권의 확정 근거로 바꾸지 않는다.
5. 5개 작업자는 보존 화면과 거래 자료를 병렬 분석한다. 공유 Chrome은 본체가 담당하며 탐색을 순차 처리한다. 작업자에게 UI를 배정할 때도 한 번에 한 담당자만 조작한다. 화면 한 페이지를 전체 history로 표시하지 않는다.

Native checkpoint, wallet resolution, RZD/연우 state는 임의 변경하지 않는다. 외부 API 한도/비용, SQLite 기준 저장과 원문·정확 수량·UTC·coverage 규칙은 [공통 운영 계획](parallel-investigation.md)을 유지한다.
